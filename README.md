# BMW E90 PT-CAN Display

Дополнительная приборка на Arduino Nano. Пассивно слушает моторную шину
PT-CAN и выводит на OLED температуры охлаждающей жидкости, масла двигателя и
**масла АКПП** и напряжение бортсети. При перегреве двигателя или коробки
мигает светодиодом и пищит.

## Целевая машина

**BMW E90 318i, 2011 (LCI), N46B20 бензин, АКПП ZF 6HP19.**

Что из этого следует:

- **N46 бензиновый → температура масла двигателя доступна.** Пустой байт `0xFF`
  в `0x1D0` — особенность дизелей N47, к вам не относится.
- **ZF 6HP19 совпадает с эталонным стендом**, с которого сняты захваты в
  DBC-mega-merge; эталонные логи сняты с E90 LCI — то же поколение.
- **2011 год → на контактах 6/14 колодки D-CAN**, а не PT-CAN. Переход
  произошёл около 03/2007. К PT-CAN подключаемся не через OBD (см. ниже).

## Шины E90 и что на какой лежит

Три шины, на глаз неразличимые:

| Шина | Скорость | Что даёт |
|---|---|---|
| **PT-CAN** | 500 кбит/с | мотор, EGS, **температура масла АКПП** |
| K-CAN | 100 кбит/с | кузов, приборка, топливо по бакам, кнопки руля |
| D-CAN | 500 кбит/с | диагностика, молчит пока не спросят |

Устройство сделано под **PT-CAN**: только там вещается температура масла
коробки (`0x0B5`, сигнал `TEMP_GRB`). Подключение — два провода к CAN H и
CAN L в любом удобном месте: блок JBE, CAS, разъём у коробки.

| Параметр | Где | Состояние |
|---|---|---|
| Температура ОЖ | `0x1D0` B0 | работает |
| Температура масла двигателя | `0x1D0` B1 | работает (бензин) |
| **Температура масла АКПП** | `0x0B5` B7 | **работает** |
| Напряжение бортсети | `0x3B4` | работает |
| Температура впуска | не найдено на PT-CAN | **разведка** |
| Топливо | `0x349` — это K-CAN | **разведка** |

Топливо по бакам в литрах есть только на K-CAN, температуры впуска в нашем
DBC нет вообще. Места в вёрстке под оба параметра готовы и заняты прочерками.

### Как достать недостающее

На PT-CAN, помимо вещания, есть **адресный UDS-канал** к блокам напрямую:

| Блок | Запрос | Ответ |
|---|---|---|
| DME (двигатель) | `0x600` | `0x608` |
| EGS (ZF 6HP19) | `0x604` | `0x60C` |
| DSC (ABS) | `0x612` | `0x61A` |

Туда шлётся сервис UDS `0x22` с идентификатором данных. По DBC, `0x60C`
держит адаптации коробки и калибровки температуры ATF. Идентификаторы
публично не документированы — нащупываются сканером на живой машине.

## Разведка перед установкой

Пошаговая инструкция для работы на машине — от проверок на столе до
подключения к PT-CAN: **[docs/field-test.md](docs/field-test.md)**.

```bash
pio run -e sniffer -t upload && pio device monitor
```

Сканер дважды по 10 секунд слушает молча — на 100 и на 500 кбит/с, потому что
на неверной скорости любая шина выглядит немой. Затем печатает словарь ID и
сверяет его с маркерами известной принадлежности:

```
0x1D0   412   8B FF 6A C8 ...   <- [B] EngineData coolant/oil
0x0B5   205   00 00 .. .. 78    <- [P] EGS torque + ATF temp
markers: PT-CAN-only 1, K-CAN-only 0
=> PT-CAN. lib/PtCan decoders apply. ATF temp available.
```

`[P]` — только PT-CAN, `[K]` — только K-CAN, `[B]` — есть на обеих (DME
вещает, шлюз ретранслирует). Дальше свип стандартных PID `0x00..0xA0`.

### Откуда взяты определения сигналов

Из репозитория **DBC-mega-merge** (`bmw_e9x_e8x1_merged.dbc`), лежащего рядом
в `../DBC-mega-merge`. Это сведённый DBC по E8x/E9x, собранный из opendbc,
loopybunny.co.uk и форумных источников и дополненный захватами с живой машины
и HIL-стенда.

Кадры DME проверены тестами на **реальных байтах** из
`tools/known_values.json` — это самые частые значения из логов:

| Кадр | Захваченные байты | Результат декодера |
|---|---|---|
| `0x1D0` | `8B FF 6A C8 ...` | ОЖ 91 °C, масло отсутствует (`0xFF`, N47) |
| `0x3B4` | `CB F3 00 FC ...` | 14.57 В |

Кадр EGS `0x0B5` на K-CAN не выходит, поэтому байтов с живой машины у нас
нет: его декодер проверен **только по DBC** — разрядность, смещение и
формула. Это единственная непроверенная эмпирически часть.

Полезные соседи по теме [github.com/topics/e90](https://github.com/topics/e90):

| Репозиторий | Чем полезен |
|---|---|
| `veikkos/e90-can-cluster` | распиновка разъёма приборки, предупреждение про терминатор |
| `Maseg535/E90-and-e8x-DBC-mega-merge-project` | тот самый DBC, который мы используем |
| `ilicmiljan/open-can-controller` | управление приборкой E9x по K-CAN через KWP2000 |

## Симулятор дисплея

```bash
./sim/build.sh          # -> sim/out/screens.png
```

Рисует все состояния экрана в картинку, без железа и без машины. Это не макет:
симулятор гоняет **тот же самый `lib/Screen`**, что и прошивка, поверх C-ядра
u8g2, собранного под macOS. Разъехаться с реальным выводом он не может по
построению.

На AVR u8g2 рисует по страницам в буфер на 128 байт, на хосте — в полный буфер
128×64, куда симулятор заглядывает напрямую. Дисплей и шина не нужны, колбэки
вывода заглушены. Дальше буфер раскрашивается по физическому делению матрицы:
строки 0–15 жёлтым, 16–63 синим.

Именно поэтому `lib/Screen` написан на **C-API u8g2**, а не на Arduino-обёртке
`U8g2lib.h`: C-ядро переносимо, а обёртка тянет за собой `Print` и весь
Arduino. Побочная выгода — форматирование чисел там сделано вручную, без
`sprintf`, который на AVR стоит около полутора килобайт.

Сценарии перечислены в `build_scenarios()` в `sim/sim_main.cpp`. Первая сборка
компилирует C-ядро u8g2 и кэширует объектники в `sim/out/`, дальше мгновенно.

## Грабли

Собрано по ходу разработки. Большинство пунктов стоили бы вечера отладки.

### Без аппаратных фильтров MCP2515 кадры теряются молча

PT-CAN на 500 кбит/с даёт порядка 1500–2000 кадров в секунду. У MCP2515 два
приёмных буфера, и Nano разгребает их по SPI — без фильтров переполнение
гарантировано, причём **без единого признака в логах**.

Прошивка настраивает маски `0x7FF` (точное совпадение всех 11 бит) и все шесть
фильтров. Нужных ID сейчас три, остальные фильтры дублируют последний: пустой
фильтр пропускал бы всё подряд. Три свободных — запас под то, что найдёт
разведка. Список в `kWanted` в `src/main.cpp`.

### FastLED.show() нельзя дёргать в каждом проходе loop()

На AVR `show()` запрещает прерывания на всё время передачи данных в ленту.
Если вызывать его безусловно каждый проход, процессор проводит с
запрещёнными прерываниями почти всё время. Последствия неочевидные и
неприятные: **начинает отставать `millis()`** — а на нём висит вся логика
протухания данных, — ломается `tone()`, которому нужен таймерный ISR, и
страдает приём по I2C.

Правильно — вызывать только при смене состояния светодиода. Мигание с
периодом 400 мс даёт пару вызовов в секунду вместо тысяч. Реализовано в
`update_alerts()` в `src/main.cpp` через сравнение с прошлым состоянием.

### Сторожевой таймер и загрузчик

`wdt_enable(WDTO_2S)` в конце `setup()`, `wdt_reset()` в начале `loop()`.
Устройство живёт в машине без присмотра, зависший блок там никто не
перезагрузит.

Работает это безопасно **только потому, что плата на новом загрузчике**
(Optiboot, `board = nanoatmega328new`): он сбрасывает флаг `WDRF` и снимает
таймер при старте. Со старым загрузчиком срабатывание сторожевого таймера
загоняло плату в бесконечную перезагрузку, и спасала только перепрошивка
программатором.

В `sniffer` сторожевой таймер намеренно не включён: его фазы переписи длятся
по 10 секунд в одном блокирующем цикле, и таймер пришлось бы сбрасывать
изнутри. Инструмент запускается под присмотром, смысла в нём нет.

### Терминатор 120 Ом на модуле MCP2515 надо снять

Дешёвые платы приходят с напаянным резистором 120 Ом между CAN H и CAN L. Он
нужен при построении шины с нуля и **вреден при подключении к существующей**:
у исправной шины уже есть два своих терминатора, суммарно 60 Ом. Третий
опускает сопротивление до 40 Ом, и связь начинает сыпаться.

Симптом коварный: работает «через раз» или падает при прогреве. Проверяется
мультиметром на обесточенном модуле между CAN H и CAN L — увидите ~120 Ом,
резистор надо выпаять (на части плат вместо него перемычка).

Источник: README проекта
[veikkos/e90-can-cluster](https://github.com/veikkos/e90-can-cluster) —
«There should NOT be 120 Ohm termination in the CAN bus adapter».

### mcp_can хочет `unsigned long`, а не `uint32_t`

`readMsgBuf()` объявлен как `readMsgBuf(INT32U *id, ...)`, где `INT32U` — это
`unsigned long`. На AVR `uint32_t` и `unsigned long` — один и тот же тип,
поэтому `uint32_t id` собирается без нареканий, **но**:

- IntelliSense в VS Code разбирает файл в модели хоста, где `uint32_t` это
  `unsigned int`, и ругается «нет перегрузки» при зелёном `pio run`;
- на STM32 и ESP32 `uint32_t` тоже `unsigned int`, и там это станет настоящей
  ошибкой компиляции.

Поэтому во всех вызовах переменная объявлена как `unsigned long`. Правка
`.vscode/c_cpp_properties.json` не помогает: файл генерируется заново.

### MCP2515: кварц 8 или 16 МГц

В `platformio.ini` стоит `-D MCP2515_CRYSTAL_MHZ=8`. Дешёвые платы выпускают
с обоими кварцами — **посмотрите маркировку на кристалле** и поправьте флаг.
При неверном значении тайминги бит-рейта считаются неправильно, и CAN либо не
поднимется, либо будет сыпать мусором.

### Байт масла двигателя может быть `0xFF`

На дизелях N47 `0x1D0` B1 всегда `0xFF`. Наивная формула `raw - 48` дала бы
207 °C и постоянную ложную тревогу перегрева, поэтому декодер это значение
отбрасывает. На вашем N46 байт должен быть живым.

### Жёлто-синий OLED: граница на строке 16

Двухцветность физическая, а не программная: строки 0–15 всегда жёлтые, 16–63
всегда синие, границу не подвинуть. Крупный шрифт, поставленный без учёта
этого, разрезается пополам и выглядит как брак.

Вёрстка это учитывает: жёлтая полоса отдана под статус, все данные лежат
целиком ниже строки 16, четыре строки с baseline 27 / 38 / 49 / 60.

### tone() и FastLED делят прерывания

`tone()` на AVR всегда занимает Timer2 независимо от выбранной ноги, а
`FastLED.show()` кратко запрещает прерывания. На одном диоде пауза мизерная,
но если услышите щелчки в писке — причина здесь.

### Mini360 настраивается до подключения нагрузки

Подстроечник выставляется **до** того, как к выходу подключена электроника.
Иначе на выходе может оказаться входное напряжение, и Nano вместе с дисплеем
уходит в утиль за секунду.

### Прочее

- Плата с TYPE-C и CH340 — почти всегда **new bootloader** (115200), отсюда
  `board = nanoatmega328new`. Со старым `nanoatmega328` прошивка не зальётся.
- Если порт не появляется в `ls /dev/cu.*`, нужен драйвер CH340:
  `brew install --cask wch-ch34x-usb-serial-driver`.
- Основная прошивка не открывает Serial и **ничего не передаёт в шину**
  (`MCP_LISTENONLY`). Для отладки пользуйтесь env `sniffer`.

## Память

```
RAM:   54.4% (1114 / 2048)
Flash: 60.5% (18580 / 30720)
```

Запаса ~12 КБ флеша. Полнокадровый режим U8g2 (буфер 1024 байта) на Nano не
помещается, поэтому используется page-режим: буфер 128 байт, отрисовка циклом
`firstPage()/nextPage()`.

### Что сколько стоит

Замерено на этом проекте, каждый пункт — отдельная сборка:

| Что | Flash |
|---|---|
| Библиотека FastLED | **3018 байт** |
| Печать `float` (`print(x, 1)`) | **758 байт** |
| Крупный шрифт `logisoso20_tn` | 402 байта |
| `Serial.begin()` | 106 байт |

FastLED — самый дорогой компонент, и это плата за **саму библиотеку**, а не за
диоды: каждый стоит 3 байта RAM, разница между одним и пятью — двенадцать
байт. Для единственного светодиода 3 КБ расточительно; альтернатива — ручной
бит-бэнг WS2812 примерно на 100 байт, но там критичные тайминги.

Печать float тянет `dtostrf`. В проекте она не используется: значения хранятся
целыми в десятых долях и печатаются вручную.

### Стоит ли покупать «расширение памяти»

**Нет — для этой задачи такого модуля не существует.** ATmega328P построен по
гарвардской архитектуре и выполняет код **только из внутренней флеш-памяти**.
SD-карта, EEPROM, SPI-флешка хранят *данные*, а не исполняемый код.

Если проект перерастёт 32 КБ, вариант один — сменить плату:

| Плата | Флеш / RAM | Что переделать |
|---|---|---|
| **Mega 2560 Pro Mini** | 256 КБ / 8 КБ | только номера ног, логика 5 В |
| **STM32F103 «Blue Pill»** | 64–128 КБ / 20 КБ | встроенный CAN, логика 3.3 В |
| **ESP32** | 4 МБ / 520 КБ | встроенный CAN, Wi-Fi, логика 3.3 В |

При нынешних 60 % это теоретически.
