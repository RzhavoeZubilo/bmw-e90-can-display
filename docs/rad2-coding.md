# Магнитола RAD2: почему не кодируется через D-CAN

Тема соседняя с основным проектом — здесь про кодирование головного
устройства, а не про наш прибор. Лежит в этом репозитории, потому что
собрано теми же инструментами и по тем же данным.

**Блок:** BMW Radio Professional CD, `6512 9258170-01`, `BMWRCD 202-35`,
Bluetooth, Чехия, 04/2011. Машина: E90 318i 2011 LCI.

**Симптом:** `SG_CODIEREN` и даже `CODIERDATEN_LESEN` в NCS Expert падают с
«ошибка CABD! смотри CABI.ERR und ERROR.LOG». Считается, что блок кодируется
только через ICOM.

---

## Диагноз

**Блок относится к семейству данных `RAD22`, а не `RAD2`.**

Трейс `FSW_PSW`, снятый через ICOM, прогнан через парсер данных кодирования
и сопоставлен со всеми 339 файлами `.Cxx` для кузова E89:

| Файл данных | Совпадение с трейсом |
|---|---|
| **`RAD22.C34`** | **81.4 %** |
| `RAD22.C32` | 73.5 % |
| `RAD22.C31` | 62.8 % |
| `RAD22.C33` | 61.9 % |
| `RAD22.C20` | 43.4 % |
| `RAD2.C03/04/50/51` | **ниже порога, в кандидаты не попали** |

Из 113 строк трейса 92 совпали с `RAD22.C34` по именам параметров; остальные
21 — это не параметры, а их значения (`E90_HIFI`, `E81_TOP_HIFI` и подобные),
которые в трейсе идут отдельными строками.

Иначе говоря: **это `RAD22` с индексом кодирования 34.**

### Почему тогда CABD

Файлы данных кодирования именуются `<семейство>.C<индекс>`. В каталоге лежат:

```
RAD2.C03   RAD2.C04   RAD2.C50   RAD2.C51
RAD22.C20  RAD22.C31  RAD22.C32  RAD22.C33  RAD22.C34
```

**`RAD2.C34` не существует.** Если NCS Expert выбирает для этого блока
семейство `RAD2` (по профилю или по имени SGBD — `RAD2.prg` в каталоге есть,
а `RAD22.prg` нет), то при индексе 34 он ищет несуществующий файл. CABD не
может собрать данные и падает.

### Почему это не про кабель

**ICOM против K+DCAN — разница транспорта, а не логики кодирования.** NCS
Expert работает через EDIABAS, а тот умеет оба интерфейса. Если бы дело было
в железе, ошибка была бы коммуникационной: нет ответа, таймаут.

Решающий довод: падает и `CODIERDATEN_LESEN`. Чтение безобидно, блок его не
запрещает. Значит отказывает не блок, а разбор данных **на компьютере**, до
всякого обмена с машиной. CABD — компонент ПК.

ICOM «работает» потому, что ISTA-P везёт свои данные и сам выбирает нужное
семейство.

## Что проверить на машине

1. **Прочитать `CABI.ERR` и `ERROR.LOG`.** Сообщение прямо на них указывает,
   и там обычно назван конкретный отсутствующий файл. Это подтвердит или
   опровергнет диагноз за минуту.
2. **Прочитать индекс кодирования блока** — job `C_CI_LESEN` через Tool32.
   Чтение, риска нет. Ожидаемое значение — 34.
3. **Проверить, какую версию SP-Daten видит NCS Expert.** На диске лежат
   67.1 и 69.0; `RAD22.C34` найден в 69.0.

Если `C_CI_LESEN` вернёт 34, а NCS Expert ищет `RAD2.C34` — диагноз
подтверждён, и вопрос сводится к тому, чтобы указать ему семейство `RAD22`.

## Расшифровка индексов кодирования

Индексы идут по возрастанию функциональности. Ниже — что добавляет каждый
следующий относительно предыдущего.

| Индекс | Опций | Что появляется |
|---|---|---|
| `RAD2.C03` | 55 | базовый набор |
| `RAD2.C04` | 57 | `M_GROUP`, `USB_RAD2` |
| `RAD2.C50` | 75 | гонги, `COUNTRYCODE_RADIO_2`, концепция микширования |
| `RAD2.C51` | 81 | `MCA`, `BASS_MSA`, навигационные уровни |
| `RAD22.C20` | 70 | маршрутизация звука, лимитеры, `AUX_RAD22` |
| `RAD22.C31` | 83 | **INBOX-группа**: Bluetooth, распознавание речи, `DAB_INBOX`, микрофон |
| `RAD22.C32` | 86 | `SECOND_USB`, `RAD22_MDRIVE`, параметры с суффиксом `_32` |
| `RAD22.C33` | 83 | вариант C32 с суффиксом `_B` вместо `_32` |
| **`RAD22.C34`** | **94** | `DAB_STANDARD_RAD` (DAB+), `CALL_WAITING_INBOX`, `FADER`, `COLORSWITCH_E84` |

Быстрые признаки принадлежности:

| Параметр | Встречается в |
|---|---|
| `BT_MODUL_INBOX_ON_OFF`, `MICROPHONE_INBOX`, `DAB_INBOX` | C31, C32, C33, C34 |
| `SECOND_USB` | C32, C34 |
| `DAB_STANDARD_RAD`, `CALL_WAITING_INBOX`, `COLORSWITCH_E84` | **только C34** |

В вашем трейсе есть `DAB_STANDARD_RAD = dab_plus`, `CALL_WAITING_INBOX` и
`SECOND_USB` — то есть однозначно **C34**, самый поздний индекс из
имеющихся. Что согласуется с датой выпуска 04/2011.

## Про вывод параметров на экран магнитолы

Ответ тот же, что был по приборке: **магнитола показывает только то, что
умеет её прошивка**, а кодирование лишь выбирает из готового набора. Вывести
туда наши значения — температуру масла АКПП, впуск — нельзя без правки
прошивки.

Штатные пункты (средний расход, забортная) включаются кодированием. В вашем
трейсе видны кандидаты:

| Параметр | Текущее значение |
|---|---|
| `CAR_COMP_ACTIVE` | `aktiv` |
| `V_INFO_RAD2` | `nicht_aktiv` |
| `MY_INFO_RAD2_20` | `nicht_aktiv` |

Что именно за ними стоит — надо смотреть в описании функций; имена
параметров в SWT-словарях даны без развёрнутых пояснений.

**Осторожно:** `20.00`-подобные параметры и всё, что меняет уровни и
лимитеры, — это запись в блок. Читать безопасно, писать нет, а у вас уже
есть рабочий путь через ICOM.

## Как воспроизвести разбор

```bash
cd /Users/densh/Work/Develop/BMW/BimmerDaten
python3 - <<'EOF'
import sys; sys.path.insert(0,'.')
from daten_parser import parse_trc, detect_module_from_trc
D = ".../BMW SP-Daten 69.0/E89/daten"
trc = parse_trc("путь/к/FSW_PSW.TRC")
for f, r in detect_module_from_trc(set(trc.keys()), D, ""):
    print(f, f"{r*100:.1f}%")
EOF
```

Парсер шумит в stderr на части посторонних файлов — это не мешает, вывод
берётся из stdout.

Словари имён: `SWTFSW03.dat` (функции) и `SWTPSW03.dat` (значения) в том же
каталоге `daten`.
